# Authova host admission and test contract v1

This is a **source interface**, not evidence that a test or production deployment
ran. `scripts/ci/host_adapter.py` implements private admission/ledger reads,
independent HMAC verification, same-inode operation locking, whole current CAS,
durable nonce+intent consumption and the owner operation sequence. The host worker
must pin/install this code outside the checkout and import `execute_files`.
No ordinary CI command can supply executable code, an approval flag or a shell.

Remaining activation blockers are concrete: wire the installed Authova
Core/Console private preflight/selective release producer to the five owner methods
below; implement the fresh CI deployment's nine-check HTTP runner; finish the CI
worker's API-backed durable issuance ledger and COPY-only packager. Pure boundary
or model tests do **not** close those gaps. Agent stays held and poller disabled.

## Independent authorization and ledger

The carrier is exactly the platform `AUTHOVA-HOST-PROTOCOL.md` v1: two envelope
fields, twelve payload fields, canonical UTF-8 sorted compact JSON without newline,
`hmac-sha256:` signature, integer UTC lifetime at most300s. Test review fields are
null; production requires the native `rwasayc` review. Future review times, bool
pipeline/time fields, duplicate JSON keys, UTF-16, altered candidate/action and
expired carriers refuse. No signing key is generated by these product scripts.

The host worker installs a fresh private0700 binding directory containing:

- `binding.json`: owner binding below, installed by the owner/worker, never a job;
- `key`: raw >=32bytes, private0600, RAM only, never content-hashed;
- the requested admission file: private0600, max64KiB;
- `test-receipt.json`: production only, complete private test receipt, max256KiB.

Every path component is opened without following symlinks. Each read checks
regular0600/singlelink/expected OS owner, bounded complete bytes, same-FD before/after
identity and final path identity; all closes are attempted. The same original
operation UTC/monotonic origins precede these reads and continue through execution.
The installed worker reports only fixed errors, never exception strings/tracebacks.

A separate **fixed worker ledger root**, private0700 and inaccessible to CI jobs,
has `<signed nonce>.json`, private0600/singlelink. Its exact nine keys are:

```
schema = authova-host-admission-ledger/v1
nonce, action, candidate_digest
payload_sha256
build_pipeline, test_pipeline, production_pipeline
test_receipt_sha256
```

The six payload binding values equal the signed fields with exact types.
`payload_sha256` hashes canonical **complete** payload (no `sha256:` prefix).
Production `test_receipt_sha256` hashes canonical **complete** owner receipt;
test admissions use null. A caller-supplied receipt cannot replace that record.
The worker independently binds its actual WP API responses and original executor
return to this immutable record. The product verifier cannot certify API provenance
from uploaded JSON; host ownership and the fixed ledger root are essential.

The owner has a separate persistent0700 execution-state root. It holds
`operation.lock` and `<nonce>.intent.json`/`<nonce>.result.json`.
Under nonblocking flock, lock inode/path identity must stay equal. Any existing
intent refuses **before service queries**. After read-only preflight and a second
whole-current CAS, the owner EXCL-writes/fsyncs/closes intent and fsyncs the directory
before the first possible service mutation. The intent is also nonce consumption;
a failed or partially written intent is retained, never removed for a retry.
Admission expiry is rechecked immediately before mutation. The worker additionally
needs its own per-pipeline issuance/consumption ledger: changing a nonce cannot
make an uncertain deployment replayable.

Operation caps use the original local dual clock, with no cross-process monotonic
values. Backend methods must check the supplied guard around operations and fit
whole operation/close/remaining suffix caps. A durable result written before the
last guard is not an original successful return; the worker must bind **both**.
Original exceptions remain first; close failures attach only fixed secondary codes.

## Owner binding and installed operations

`authova-owner-binding/v1` exact keys:
`schema,action,candidate,project,current,seconds,fixture`.
Candidate is the existing exact eight-field object; seconds is a trusted integer
60..1800 total cap, not an arbitrary job timeout or a measured fit claim.
`current` has exact keys `schema,project,schemaDigest,layers,services`, with schema
`authova-owner-current/v1`. `layers` retains **all** active layer paths in order.
`services` is exactly core/console, each exact `{id,image}`; production values are
full actual CID/image IDs. This object contains only public IDs/paths, never Env,
DSN, secret bodies or secret-derived hashes. The backend compares private config
semantics only in controlled memory; `current` is not a substitute for that check.
Schema digest changes refuse automatic deployment.

Production project is only `authova-local-production-20261114`; fixture is null.
There is no password/account/session/OIDC mutation in production acceptance.
Selective up keeps `--no-deps --no-build --pull never --wait --wait-timeout90 core
console`, all original layers and volumes. Only the two immutable image IDs and
Console `/opt/authova-console/web` assets field may change. No migration, rebuild,
DB/Worker action, shared route, issuer/key/TOTP/trust change or implicit pull.

Test project is exactly `authova-ci-test-<source12>-<build_pipeline>`. It is derived
from the known build number; no nonexistent test pipeline number is invented at
test admission. The subsequent actual test pipeline is independently ledger-bound.
`fixture` exact keys are `schema,scope,root,network,mysql_volume,service_names`:

- schema `authova-ci-test-binding/v1`, scope fresh32lowerhex;
- root `<owner state root>/test/<scope>`; only layer `<root>/compose.json`;
- network `<project>-network`, MySQL volume `<project>-mysql`;
- service_names maps exactly core/console/mysql/valkey to `<project>-<role>`;
- current core/console `{id:null,image:null}`; any existing target must refuse.

The actual fixture producer must verify this namespace is absent before creating
resources; create a **new empty** DB, runtime/migrator identities, keys, test-only
operators/App-users/clients and isolated normal-TLS endpoint. It must not clone
production data or read/mount production env, secrets, volumes, routes or accounts.
CI test initialization is distinct from a production migration. Fixture credentials
are private new test material, never uploaded. Labels/CID ACKs and known-only exact
cleanup are required; unknown resources are retained for resolution, no prune.

Installed Authova owner operations (not JSON callbacks):

| Method | Required behavior |
| --- | --- |
| `current(binding, guard)` | Fresh fixed target/singleton IDs plus complete current owner control; no broad scan, secret output or inferred whole-CAS |
| `preflight(binding, guard)` | Read-only private config/current-service comparison, immutable local image existence, actual read-only DB/schema/privileges; test fresh-namespace isolation |
| `apply(binding, guard)` | The fixed two-service operation; only `APPLIED` or `FAILED_KNOWN`; any exception/other result stops unknown, no replay |
| `accept(binding, guard)` | Production: non-destructive readiness/assets/guest/config/schema/same-volume gates, `PASS`/`FAIL_KNOWN`; test: actual full receipt below |
| `rollback(binding, guard)` | Production known failure only, fresh known poststate/ownership CAS, exact old images+all old layers, same volumes, no data restore; return `ROLLED_BACK` only after verification |

The adapter does not interpret a dictionary as these installed operations. Wiring a
stub or model backend does not make the executor operational. On any unknown
mutation/acceptance/wait/close, it leaves consumed intent, no automatic rollback or
replay. Test failures never invoke a production rollback method.

## Fixed owner test checks and receipt

The **trusted installed owner source**, not candidate/job fields, fixes these nine
IDs. `checks` must contain exactly these IDs, each string `PASS`. `check_evidence`
contains the same IDs with actual native outcomes. All mutations below are limited
to this binding's fresh CI users/clients/sessions.

| ID | Required actual behavior |
| --- | --- |
| `artifact-identity` | Core/Console runtime IDs and manifest/archive/binaries/assets match the same candidate; test does not rebuild |
| `fresh-fixture-schema-and-privileges` | Empty test-only DB initialization; runtime role limited; version/dirty/checksum checks, no production access |
| `runtime-configuration-and-hardening` | Exact fixture labels/IDs/network/volumes/UID, RO/capdrop/NNP and intended isolated config; no production mount or route |
| `normal-tls-health-and-static-assets` | Normal CA+hostname health, UI entry and referenced assets from same Console artifact; no insecure fallback |
| `guest-and-authorization-boundaries` | Anonymous401, CSRF/role/App/operator boundaries, no privilege from caller flags |
| `management-password-mfa-logout` | Official test operator password+MFA login, failed auth, logout and old-session401 |
| `ordinary-app-oidc-pkce-lifecycle` | Fresh ordinary App-user/client real code+S256/state/nonce/RS256+kid/issuer/singleaud; repeat identity and logout; no email merge |
| `operator-password-and-session-revocation` | Own test target current-password/recent-MFA/role checks; actual password change, target-session revocation, old-proof rejection; unrelated sessions unchanged |
| `owned-test-io-and-session-closure` | Original known waits/timely completion, controlled response/log/secret lifetime and own session cleanup; resource teardown reports separate known outcomes |

Full receipt exact keys:
`schema,candidate,result,project,scope,checks,check_evidence,started_at,finished_at`.
Schema `authova-test-deployment/v1`, result `PASS`; project/scope equal actual binding.
Each evidence object exact keys:
`result,exit_code,known_return,timely,started_at,finished_at,evidence_sha256`.
Require result PASS, integer0 exit (bool rejected), both booleans true, finite ordered
original UTC within the receipt window, SHA256 of a **safe actual evidence record**,
not any private subject/credential/token/body. Missing/extra/failed/skipped/unknown
checks cannot produce a passing receipt. No caller boolean supplies native evidence.

The adapter durable-writes the test receipt before its terminal result. The worker
accepts it only with that exact original returned execution and fresh API success,
then stores its canonical SHA in the production nonce's immutable ledger. A receipt
schema validator alone cannot establish that those nine checks ran.

## Verification and limits

Run `python3 -B -m unittest discover -s scripts/tests -p 'test_ci*.py'`.
These tests use actual OWN files/flock/EXCL/fsync and a fake owner; no Docker,
HTTP, private production configuration or real keys. They distinguish admission,
ledger, CAS, nonce reuse, lock replacement, unknown-vs-known rollback, original
clock expiry and first+close failure. They are not actual deployment evidence.

Platform's `20261119-authova-fixture-startup.json` is separately reported service/CLI
startup and exact teardown evidence at source4d6. It does not run Authova Go/DB gates,
UI build, concurrent Go stress, packager, host executor or the nine test checks.
