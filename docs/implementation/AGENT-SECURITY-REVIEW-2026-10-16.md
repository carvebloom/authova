# Agent 代码与安全设计复审

日期：2026-10-16。范围：Core Agent 服务、SQL 适配与迁移、OAuth 授权/签发/刷新/内省、管理与账号接口、Contracts 资源 SDK/示例、Console 写状态机。保留此前未提交的资源隔离、Passkey 和可观测性实现。

## 1. 确认问题与修复

### F1 · P2：管理 API 未强制检查管理 scope

使用内置 Console 客户端，实际通过密码、MFA 和浏览器同意流程，只请求 `openid profile offline_access`；原实现仍允许读取管理 API，HTTP 200。之前只检查管理 audience、用户角色和 MFA，缺少对 `authova.admin` 的要求。

修复：管理 JWT 必须同时满足显式管理 scope、唯一管理 audience、内置系统客户端，以及持久化 token 的用户/客户端/会话/到期绑定。修复后此凭据返回 403。它仍然要求真实用户身份、运营角色和 MFA，不能将该问题描述成匿名取得管理员权限。

### F2 · P2：被拒绝的 Agent 刷新请求消耗原凭据

使用有效委托的刷新令牌，传入错误 installation_id 或 resource。原实现先把旧刷新令牌写为 used，再检查 Agent 接入与资源；协议错误 400 仍提交该状态。随后正确请求也失败，可能进一步触发 family 重放撤销。

修复：先完成当前用户、接入、授权和请求参数校验，成功后再原子消费旧令牌并生成替代凭据。修复后错误请求保持 400，随后正确刷新成功且 grant/tenant/user 不变；真正重放已成功使用的令牌仍撤销 family。该问题影响可用性，没有观察到它能获得另一个租户的授权。

两个问题都在修复前的真实 PostgreSQL/MySQL 上复现。原始失败日志只包含上述失败断言，随后恢复修复代码并执行最终门禁。最终结果见 [复审证据](evidence/agent-security-review-2026-10-16/summary.json)。

## 2. 纵深防护与排除的初始假设

- 管理 API 明确要求内置 Console 客户端，拒绝带有运营角色/MFA/管理 audience 的遗留业务客户端凭据。当前注册和编辑接口本来就禁止普通客户端/Agent 使用保留的管理 audience，因此没有把这项纵深防护冒称为现存公开 API 的已确认提权漏洞。
- SDK 要求 `principal_type` 与 delegated/autonomous 一致，验证 actor 和主体关系，拒绝整数溢出、非正/倒置期限及不正确的 JSON MIME 类型。这些是畸形内省响应的防护测试；没有把模拟身份服务的任意响应等同于真实 Core 可签发该凭据。
- Console 的 owner 控制、私有视图权限、未知提交冻结、CAS 后读回、一次性密钥保护已复查；本次没有修改前端权限判断来代替服务端授权。

## 3. 隔离与授权复查

| 边界 | 实现与验证 |
| --- | --- |
| App 存储 | Agent/installation/grant/token 查询与 JOIN 均包含 App 键，复合 FK；PG 启动门禁验证 24 张表的 FORCE RLS 和策略，事务使用 SET LOCAL 隔离上下文；MySQL 显式 App 条件与二进制排序规则 |
| App HTTP/凭据 | 外 App 的对象读取和撤销拒绝；Agent 凭据不能在另一个 App 换取令牌；App 运营凭据不能管理另一 App |
| 资源侧 App | 真实 Core/SDK 组合使用两个 App、相同 tenant/resource 字符串及各自有效资源凭据，App A 令牌在 App B 仍拒绝 |
| 接入身份 | Agent A 凭据不能选择 Agent B 的真实接入；自主请求中的 user_id/tenant_id/agent_mode 不会改变服务器绑定的机器主体与上下文 |
| 委托租户/用户 | 同一 Agent 对两个租户、两个 App 内用户的授权独立；刷新不能切换到另一份已批准接入；调用者附加的 tenant_id/user_id 不能改变原授权 |
| 用户自助 | 列表使用当前会话的用户，忽略伪造查询用户；用户不能撤销另一用户/租户的 grant；撤销自己的授权不影响另一份授权 |
| 管理/资源凭据 | Agent 客户端不能执行资源内省，旧 Client 编辑不能授予它内省受众；管理 scope 和 Console 客户端目的在消费处再次校验 |
| 创建回执 | 同 App 的另一 owner、另一 App 的同一 owner 均不能读取创建者的回执；GET 回执仍不含 client_secret |
| 撤销与并发 | 当前状态由主库快照读取，没有正向 allow 缓存；共享配置锁允许并发签发，排他撤销等待此前签发提交；配置版本 CAS 与失效绑定仍生效 |
| 资源业务权限 | SDK 强制要求业务回调；匹配 tenant 不替代对象/用户权限。验证伪造租户请求头无效、缺 scope/业务拒绝为 403、依赖故障为 503，均不进入业务 handler |

## 4. 凭据信任边界

**Installation 是批准记录，不是独立的部署凭据。** 同一托管 Agent 的机密客户端代表同一个服务端运行方，可使用它已经获批的不同自主接入；每个令牌只包含一个目标资源和一个租户上下文。

不同租户自行部署且互不信任的 Agent 必须分别注册独立身份和客户端密钥。不得把同一全局 client_secret 分发给这些部署。公共客户端使用 PKCE/逐用户委托，不获得共享服务端密钥。

外部组织、租户成员和租户管理员资格仍由可信业务系统核实；当前管理接口要求平台或 App owner，不提供外部租户管理员自助身份。资源 SDK 的 tenant 必须来自可信业务上下文，且业务服务继续检查当前权限与数据归属。

## 5. 本地验收及边界

本轮执行最终代码的两库全量 race 回归、真实资源 SDK 组合、Contracts 生成/lint/vet/race、Console Go/Valkey 和前端门禁，并保留修复前失败证据。具体计数、跳过项目与运行版本校验保存在上方机器证据，不把历史测试数与本轮结果累加。

本轮没有重新宣称持续 5000 QPS、千万 Agent、跨地域即时撤销、外部 Agent 客户端互操作、独立渗透测试或生产认证。离线 JWT 最多仍有 300 秒窗口；在途业务操作不会被后续撤销自动回滚。既有容量失败和外部验收门槛不变。
