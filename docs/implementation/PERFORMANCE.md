# 持续容量实测与限制

更新：2026-10-14。Apple Mac16,7、48 GiB 内存，Go 1.27.2/GOMAXPROCS=14；Docker VM 11.67 GiB，其他项目同时工作。生成器与 Core 共用宿主机，DB 在 Docker；没有改动其他项目容器或全局 Docker 配置。

## 负载定义与判定

每后端实际 COUNT=12,000,000 用户及其独立 HMAC 标识/加密 payload。RS256 user token 和 User/Session/family 关联完整。小时测试 fixture 的 TTL 为测量时长+10 分钟，避免中途自然过期；这是合成在线内省负载，正常 5 分钟 TTL/真实 refresh 另有 30 分钟测试。

开放环目标 5100 QPS，256 workers，有界队列 2048。确定性伪随机分布于报告的活跃样本；100,000 样本通过已索引的标识定位，未扫描解密全库。延迟按计划到达→响应，包含排队和 drain；直方图 0.1ms/1ms 有界，>120s 明确标记，不保存每请求延迟数组。掉队列单列，整段成功 QPS 用真实 elapsed/drain 分母。

通过条件必须预先确定持续吞吐、错误、允许丢队列及延迟。此处至少要求整段成功 >5000 QPS，并报告全部错误/drop；未达即失败，不以最好分钟替代整段。

MySQL 1h/1000 样本：15,941,369 成功、311,671 个 HTTP503、2,106,960 掉队列；4427.75 QPS，P50/P95/P99=189.8/890.6/1458ms，不通过。其运行期间曾发生数据库中断并恢复，失败不能视为正常压力通过。对中断原因保留可证事实，若未采集到退出瞬间状态，不自行认定应用漏洞或 OOM。

旧版本两分钟单库结果：PG 5097.4、MySQL 5099.8 QPS，均 0 错误/drop，P99 255.9/253.3ms。它们仅证明短测，不能覆盖本轮小时 gate 失败。其他短测和失败报告全部保留在 evidence。

## 资源与原因边界

PG 小时观测 65 次 readiness 均成功，Core RSS 范围 20.48–70.75 MiB；停止负载数分钟后 heap 7.09 MiB、16 goroutines。没有从该观测发现 Core 随请求数持续增长；不等于证明没有任何内存泄漏。负载发生器使用有界 histogram；每分钟 heap/goroutine 同时记录。

DB pool64 出现等待，不能直接把 pool 加大当作解决。PG pool128 的短测叠加 MySQL 负载后更慢，资源竞争很强；该结果没有证明连接池单变量的因果。保留 baseline、shared-load、故障、冷启动和恢复的条件，不挑选窗口或改变统计口径。

本轮优化减少 token gob 解密/解析，Client 解析缓存每次由当前主库密文验证且有界，不缓存 User/Session/family/role 的 positive active。故障 503 日志采样避免数据库中断导致日志风暴，失败指标全量累计。

## 最终修复后的短测

最终热路径五分钟复测：PG 5044.53 成功 QPS、0 HTTP 失败、16,536 掉队列，P50/P95/P99=5.6/346/617ms。服务端显式 GOMAXPROCS=6、GOGC=200、GOMEMLIMIT=384MiB、pool64；生成器 GOMAXPROCS=14，不能混淆。复测期间无本项目 MySQL 高负载，其他项目仍共享主机。

JWT 单次解析和运行参数同时变化，不能把收益单独归因某一变量；这些 GC 参数仅为本次内省画像，不直接推广至有 Argon2 密码负载的生产默认。仍有计划掉队列，且五分钟不能替代小时级持续通过。因此持续容量 gate 保持未通过。

## 正常协议 TTL 与恢复

PG 的 30 分钟子测试完成 16025 次有效检查/7 次真实 HTTP refresh；组合命令后续 MySQL 启动失败，因此组合命令整体失败。MySQL 后续独立 30 分钟通过 16228 次检查/7 次 refresh。此前 MySQL 重试在共享资源压力下超时的失败日志保留。不能把合成小时 fixture 当作正常令牌寿命/签发吞吐。

两库 12M 全量备份/恢复并比对的记录在 `review-capacity-restore.json`：PG backup73.78s/restore306.86s，MySQL 最终 restore1359.65s；两次 OOM 后限制恢复批次，详情见 OPERATIONS。这是单机完整恢复，不是跨机 HA/客户 RPO/RTO。

## 重跑与尚未证明

`authova-load -users 12000000` 建立真实容量库；私有 `.dev/load-*.json` 不入库。`authova-bench -qps 5100 -duration 1h -workers 256 -progress ... -report ...`；`-samples 100000` 增加工作集，`-server-url` 仅替换测试传输入口，不改持久化 issuer。`scripts/observe-soak.py` 每分钟记录资源和 readiness。

目前目标持续容量未获通过证明。下一次容量验证应采用独立生成器/专用数据库和明确硬件预算，串行容量与恢复/build；先定位 CPU、DB 等待/IO 和队列，再优化或增加实例。不能牺牲强隔离、主库撤销查询或错误语义换取吞吐。

未证明：5000 密码 KDF/refresh/签发/短信吞吐、全部 12M 同时活跃随机 token、攻击画像、多机故障转移/多区域，以及客户延迟 SLO。远端 CI 未运行、未 push。
