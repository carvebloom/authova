## 真实 Chrome / 协议验证

九个选定场景的明细见 `browser-scenarios.json`，是本轮验收分母，不是全产品覆盖率：

- 管理端保存仅手机 OTP 策略；终端页面无密码/注册入口，邮箱选项禁用，手机已选中；通过 UI 恢复原六开关。
- 禁用→恢复用户，权威读回 active，原两条会话仍 revoked；随后密码 + 当前 TOTP 可重新认证并进入账号安全页。
- UI 创建/轮换机密 Client，密钥仅一次展示并显式关闭；实际 token endpoint 在重叠期对新旧凭据均返回 200，UI 撤销前一份凭据后旧凭据 401、新凭据 200。
- UI 常规轮换使 JWKS 保留两份 key；UI 应急吊销旧 key 后 JWKS 只剩当前一份，元数据记录 revoked_at。吊销当前 signer/两个独立 Provider 预热缓存场景由真实两库测试验证。
- 实际账号 TOTP 换绑、丢失认证器恢复登录强制设置新 TOTP、当前 TOTP 重新生成恢复码，均确认新码十份及旧会话失效。MFA 浏览器链路在本轮较早运行，最终源码由 16 场景继续覆盖；不公开 seed 或码。
- 策略页/密钥页 375px 的文档宽度等于 viewport；亮色和深色截图已查看。不是全站 WCAG、读屏或所有设备认证。

专用 MFA 验收 App 的 QA callback 返回 404；此处只验证授权完成与账号 Cookie，不称该 callback 已执行 token exchange。原有真实 RP 交换/refresh/introspection 由既有五条浏览器回归负责。

## 实际发现并修复的问题

1. MySQL 不接受 TEXT 的该默认值定义。核对 v3 dirty、新列零新增与历史后，解除 dirty 并使用有界 VARCHAR 完成正式 v4；PG 已执行内容未改写。
2. 新策略下安全解绑仍可能把已禁用登录方式算成后路。改为按当前策略和实际已验证别名判断，并补真实两库回归。
3. Client secret 对话框初始权威读取失败后仍可提交旧列表版本；现在读取失败禁用轮换，并允许重新读取。
4. 空宽限期经数值转换变为零，可能误触立即切换；现在空值被拒绝，零秒必须显式输入。
5. HTTP 200 缺少关键状态/密钥字段时可能被当成功。五项新增写 API 检查关键确认字段；异常按结果未知冻结、读回，不自动重放。
6. 原 OTP 集成测试跨 fixture 误取别人的 outbox 码；改为按 App 和收件人筛选。既有安全测试按新 CAS 契约递增配置版本。
7. 手工重启漏启投递 worker 导致短信/邮件回归超时；已恢复独立 worker。持久化 Demo 的运营账号超过一页，旧浏览器测试误以为新账号在第一页；修正了初始路由/表格等待、翻页追加等待、保存后回到第一页的读回。失败轮次保留，不计为产品通过。

保留复现输出与修复后输出。StrictMode 初始读取专项通过，未发现该项回归；不将排查猜测写成已确认缺陷。
