# 5. 容量、可靠性与自部署运维

## 5.1 先把 5000 QPS 说清楚

5000 QPS 是目标，尚无测量证据。“鉴权”至少有四条不同路径，不可把边缘本地 JWT 验签的 QPS 当成 Authova 服务端登录 QPS。

| 场景 | 是否到 Authova | 主要成本 | 首次验收负载候选 |
| --- | --- | --- | --- |
| 本地 access JWT 验签 | 通常否；只在 JWKS 轮换时取公钥 | 资源服务 CPU/公钥缓存 | 资源服务总体 ≥5000 QPS，验证兼容及轮换；单独报告 |
| 在线 Introspection | 是 | 主库状态读取、Token 校验、网络 | 稳态 ≥5000 QPS，含热 App 和退出/封号 |
| Refresh | 是 | 数据库行锁/写、签名、审计 | 独立峰值压测，并在混合负载中占比指定 |
| 交互登录（密码/OTP/OIDC） | 是 | 密码 KDF CPU、数据库写、供应商延迟 | 独立峰值压测，明确密码/OTP/第三方比例 |

在用户给出真实业务比例前，先准备一套**评审用**压测组合：持续 30 分钟 6000 QPS，其中 4800 在线内省（全部新主库快照，不缓存 positive active）、900 refresh、300 交互登录（密码/OTP/外部 OIDC 各 1/3）；最大 App 占 80% 请求。另测 60 秒 1.5 倍突发和 24 小时 70% 峰值耐久。它只是验收脚本起点，不能当作用户已确认的负载，也不能把外部供应商响应时间归功于核心服务。在线内省 5000 QPS、refresh 5000 QPS、密码登录 5000 QPS 还需分别测极限并报告所需硬件，避免混合流量掩盖单一路径瓶颈。

若 5000 次/秒都做 100ms 单核 CPU 密码验证，纯 KDF 理论需求约 **500 CPU 核**（不含协议、数据库和冗余）；若 5000 QPS 多数是本地验签，Authova 核心负载则完全不同。这只是排容量级别的算术示意，真实 KDF 时间依硬件/参数测定。先按混合流量设计，但必须请需求方定实际比例、突发持续时间、单大 App 占比和跨区延迟，再冻结验收报告。

粗估公式还包括：`稳定 refresh QPS ≈ 同时活跃且需刷新的 Session 数 / 平均刷新间隔（秒）`。例如 100 万活跃 Session、平均每 10 分钟刷新一次，约 1667 QPS；500 万则约 8333 QPS。真实流量会因空闲、抖动和到期同步产生尖峰，Client 应在合理范围内加入随机抖动。5000 QPS 全天持续是每天 4.32 亿次请求；若每次都写 500 字节审计事件，仅原始事件就约 216 GB/天（不含索引、WAL、复制和备份）。因此安全敏感的状态变更/认证事件做事务内持久审计；高频内省的逐次读取日志按租户配置、风险等级、采样或专用日志存储，指标必须保留完整计数。不能把每次内省同步写主库并假定容量无代价。

## 5.2 容量模型与压测数据

基准数据至少 1200 万 active User，另有停用/历史标识、凭据、外部绑定、Session、refresh、audit/outbox/固定管理员授权；不得只有空用户表。设计两种分布：A 是多 App 长尾 + 最大 App 占 40%；B 是最大 App 占 80% 的热点。邮箱/手机号命中与未命中、用户活跃度、会话分布和 token 过期同时段应符合现实偏斜。数据量、行宽、索引大小、增长率、保留期限和磁盘余量都记录在报告。

压测矩阵对每类路径及混合负载分别测试：冷缓存、热缓存、正常/高错误率、批量会话撤销和封号、签名 key 轮换、所选数据库主备切换、Valkey 中断、供应商慢/超时、worker 积压。每次报告硬件/实例规格、Go/数据库/Valkey 版本、连接池大小、数据集 seed、App 偏斜、持续时间、P50/P95/P99、吞吐/错误率、CPU/内存/GC、DB IOPS/锁等待、缓存命中率、供应商成本。使用开放环压测，避免客户端跟不上时误报系统正常。

两后端分别执行并报告上述矩阵，不把 PG 结果当 MySQL 能力。重点记录状态读取成本、Session/refresh 基数、封号/撤销写入、主库锁等待和撤销可见性；不套用旧业务权限决策的基准。

提议的首批 SLO（评审值，不是承诺）：在线内省在正常稳态 5000 QPS 下 P99 < 100ms、成功率 ≥99.9%；Token refresh P99 < 300ms；本地密码登录端到端 P99 < 1s（不计用户输入与供应商投递）；管理写入无统一 QPS 承诺。需要按目标硬件、地理距离和内省查询计划重新定阈值。高优先级安全正确性始终先于延迟目标。

## 5.3 扩容与保护机制

- Go API 节点无本地持久状态，按 CPU/延迟/队列扩容。内部分离高 CPU 密码验证、在线内省和管理长查询的并发池/限流预算，避免登录洪峰饿死撤权与管理通道。可用独立同代码部署角色，但域模型和版本仍共享。Argon2id 等内存困难算法还受内存容量/带宽限制，不能仅按 CPU 核数扩容。
- 连接池按节点总数预算，防止 `节点数 × 每节点连接数` 压垮事务数据库。查询设置超时、批量上限、游标分页；分析慢 SQL、索引选择和锁竞争。auth code/refresh 的写热路径优先保证单行/小范围事务。
- Valkey 只作可丢弃状态：速率限制若 Valkey 不可用，按风险等级拒绝高成本/高风险请求或启用严格的本地保守配额；不能放开短信 OTP、密码暴力尝试。内省和管理授权从主库新快照判断；主库不可用时返回明确失败，不使用旧 active/allow。
- 对 App/Client/来源 IP/账户/供应商设公平性和限额，避免单热点 App 抢占所有资源。用户列表、管理导出和清理任务各有限额及预算。限流返回 `Retry-After` 与稳定错误码，但登录响应不泄露账号存在性。
- 每 App 密钥意味着 key ring 与 JWKS 缓存随 App 数量增长；密钥生成/轮换做有界队列，限制 KMS 请求速率并避免热点 App 轮换拖慢其他 App。JWKS 缓存清理必须顾及最长 token TTL，不能以节省内存为由过早丢公钥。
- 不预设按 App 分片：单个 App 可能占 80%，哈希 `app_id` 不能拆热点。瓶颈明确后先优化查询、索引、池化、只读工作和公开配置缓存；真正拆分时需要 App 路由目录、事务域边界、迁移和故障切换方案。审计/outbox 优先分区，核心身份数据后定。

## 5.4 故障语义与可用性

| 依赖故障 | 登录/签发 | 在线内省 | 既有离线 JWT | 处理与恢复 |
| --- | --- | --- | --- | --- |
| 所选事务主库不可用 | 拒绝有状态操作 | 返回依赖错误；不使用缓存返回 active | 在到期前可被资源服务验证 | 告警、切主与一致性检查；不从 Valkey 重建身份或撤销状态 |
| Valkey 故障 | 流程若持久化在事务库 可继续；高风险限流采取保守模式 | 仍读主库；按资源预算限流或拒绝 | 不受核心 Valkey 直接影响 | 防止回源击穿与数据库过载 |
| KMS/签名密钥不可用 | 拒绝新签发 | 可检查现有在线状态（若不需要签名） | 已分发公钥下可验证 | 监控 key cache/租期，禁止非授权回退 |
| 邮件/短信故障 | 相应认证/验证方式不可完成 | 不受影响 | 不受影响 | 有界重试与失败通知，不能跳过验证 |
| 上游 IdP 故障 | 对应第三方登录失败或有界重试 | 不受影响 | 不受影响 | App 可选择其他已经配置的登录方式 |
| 事件订阅方故障 | 事务成功后照常响应 | 不受影响 | 不受影响 | outbox 重试、死信和重放，订阅者幂等 |

跨可用区部署时 API 多副本、所选数据库主备及备份、Valkey 高可用、负载均衡和 KMS 可用性共同决定实际 SLA。切主后的时间线和同步级别会影响已成功响应的写入是否丢失；生产配置必须说明 RPO/RTO 并以演练证明。不能用“节点无状态”推断整体高可用。

## 5.5 自部署包、配置与升级

交付候选：带 SBOM/校验签名的版本化容器镜像、Kubernetes/Helm 部署模板、最小 Docker Compose 开发环境、配置参考、迁移工具、备份/恢复指南和兼容矩阵。生产配置必须显式给出 public origin、受信代理、数据库、密钥提供方、管理员引导方式、TLS 与生产 HA 画像的 Valkey。开发画像可省略 Valkey，但高风险限流转为保守模式。默认登录页面随 `authova` 镜像交付；Console 独立版本通过 API 兼容矩阵搭配。部署离线环境时依赖镜像与升级包可预先导入。

数据库迁移采取 expand → 兼容运行 → backfill → contract，支持滚动升级的版本窗口明确写入每版 release notes；回滚不能简单逆运行有损 SQL。迁移前备份并验证可恢复，历史数据大表 backfill 有节流/断点/进度指标。签名 key、盲索引 key 与供应商 Secret 迁移分开；密钥丢失通常不是普通数据库恢复可以解决的。首次平台 operator 通过一次性本机引导流程创建，凭据短时有效并用后作废；恢复需受控离线程序、双人审计候选，不能长期保留默认超级管理员密码。

## 5.6 观测、审计与隐私

- 指标按 App（对高基数 ID 做限额/聚合）、端点类、结果类别与依赖记录：请求速率/延迟、KDF 队列、数据库连接/锁、Valkey 命中/回源、限速触发、验证码投递状态、refresh 重用、跨 App 拒绝、key 年龄、outbox 积压、内省状态读取耗时。
- Trace 包含 request/correlation ID 和模块耗时，禁止采集 token、密码、OTP、完整联系方式。日志将事件与失败类关联，但对外错误不给敏感细节。
- 安全审计与业务操作在同事务记录最小事件，事件链可加签名/哈希校验与外部归档；“不可篡改”要有独立存储和权限控制才能声称。审计查询按平台/App 范围授权，批量导出留审计。
- 定期演练：令牌密钥泄露、管理员账号恢复、数据库恢复与只读窗口、Valkey 丢失、某 App 批量删除/恢复、供应商长时间故障、时钟漂移。将恢复时间和剩余风险记录为可复现证据。
