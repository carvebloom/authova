# 6. 正式实施、验证与待决策项

## 6.1 实施方式

每阶段交付可部署、可升级且安全边界完整的正式产品纵切面。先冻结语义与协议再扩展功能；每次变更由 `authova-contracts` 的评审草案/正式版、Go 实现、Console 适配和兼容测试共同组成。不能让 Console 直接依赖内部数据库或让 SDK 根据非公开 URL 猜 issuer。

| 阶段 | 主要交付 | 进入下一阶段的证据 |
| --- | --- | --- |
| 0. 架构基线 | 本方案评审、风险登记、协议库候选评估、App/Client/issuer/标识规则、部署最小依赖、多库事务接口与能力边界、固定管理角色矩阵、威胁模型 | 两个 App 的完整反例清单；关键未决项有负责人/期限；草案契约通过 lint |
| 1. 可信底座 | Go 服务骨架、配置/密钥接口、PG/MySQL 独立迁移、AppContext、平台首次引导、App/Client 管理、审计/outbox、健康与指标 | 两后端存储 conformance 与跨 App 查询/写入/缓存/管理负向测试；迁移/备份/恢复演练；管理员恢复审计 |
| 2. 认证闭环 | User/标识、邮箱/手机与密码、默认登录 UI、Session、OIDC code+PKCE、Discovery/JWKS、token、refresh/revoke、外部 OIDC 连接 | OIDC 互操作与安全测试；code 竞争、refresh 重用、App2 Cookie/Token 拒绝；供应商故障不绕过认证 |
| 3. 管理与接入闭环 | 固定平台/App 管理角色、管理 Console、用户/会话管理、Token 内省、审计查询/导出和 Go SDK | 管理越权/最后 owner/撤销反例、内省状态可见性、依赖失败拒绝、API/SDK 契约测试 |
| 4. 生产候选 | 高可用包、升级/回滚窗口、性能调优、故障注入、独立安全评审、运维手册、依赖与许可证审查 | 真实规模基准、目标负载矩阵、RPO/RTO 演练、安全缺陷关闭、发布兼容矩阵 |

此顺序不是“先做 demo”；阶段 1 的 App 管理、阶段 2 的登录都按正式迁移和审计规范实现。发布准备可选先内测/候选版，但不以功能“能跑”替代生产验收。

## 6.2 可形式化的关键验收

### 隔离和身份

- 用同一邮箱在 App1、App2 注册，得到不同 User、密码/外部绑定、Session、协议授权和管理范围；分别更改/禁用一个，不影响另一个。
- 从 App1 取得合法 Cookie、code、ID/access/refresh token、provider 回调、管理员 token，逐个提交到 App2 的对应入口，均拒绝；所有拒绝有可追踪 request ID，且不泄露 App2 用户存在性。
- 两后端缺 AppScope 的 repository 调用必须拒绝，跨 App FK 插入失败，查询/导出逐项验证范围。PG 额外验证人为删去 `app_id` 条件仍被 RLS 限制；MySQL 共享表没有该数据库行防线，不能用同一验收声明。各后端 schema、索引和 DB 权限独立审计，见 [存储验收](12-portable-storage.md#128-兼容与发布门槛)。
- App slug 改名不改变 issuer、`sub`、Client ID；删除/重建 App 不复用旧 issuer 和用户 ID。

### 协议、安全和并发

- code 精确绑定 App、Client、redirect URI 与 PKCE，两个并行 token 请求最多一个成功；重放拒绝。
- refresh 轮换后旧 token 重用导致该 family 撤销；并发请求至多一个成功，响应丢失时 Client 重新授权；重用检测不放过实际盗用。
- token 验证器拒绝错误 issuer/audience/typ/alg/`kid`/过期/未知 App；不能将 ID token 当业务 access token。签名轮换期间，新旧合法 token 按窗口验证；停用后拒绝。
- 密码哈希参数及 KDF CPU 在目标硬件上测量；验证码限次/过期/重复使用、账号枚举和供应商超时用负向测试覆盖。
- 独立安全测试覆盖 OAuth redirect、CSRF、XSS、Cookie、代理头伪造、外部账号绑定、管理员恢复、Secret 泄露和 SSRF（外部 issuer/回调配置）。

### 管理权限、撤销与可运维

- 固定管理员角色不得跨 App 或升级到平台；auditor 不可写入，admin 不可授予 owner；App 暂停后平台恢复路径仍可用。
- 新主库快照内省看见此前已提交的退出、封号和 App 暂停；管理 API 读取当前固定角色，不接受旧 Token 角色快照。两后端验证依赖失败不返回 active/allow、最后 owner 保护和在途敏感写入的并发边界。
- 1200 万+ 数据集和混合/单类负载各自形成报告；5000 QPS 只可对实际通过的类别、硬件、数据分布、延迟和错误率声明。报告含最长持续时间和故障恢复期间的退化情况。
- 从 N-1 版本滚动升到 N 版本、恢复备份、重放 outbox、切主、重建 Valkey、轮换 key 均演练并记录结果。若有不可逆迁移，明确恢复点与运维停机策略。

## 6.3 外部组件选择与二开策略

| 候选 | 可考虑的用途 | 在选型前必须验证 |
| --- | --- | --- |
| [Ory Fosite](https://github.com/ory/fosite) | Go OAuth2/OIDC 协议能力候选，避免自写完整协议核心 | 当前维护/许可证、需要的 OIDC 能力、每 App issuer/key 隔离、存储事务与 RFC 9700 安全行为、升级成本 |
| [go-jose/v4](https://github.com/go-jose/go-jose) | JOSE/JWT 加解签候选 | 算法白名单、JWT profile 支持、Go 版本、许可证、密钥轮换与兼容测试 |
| pgx/v5、go-sql-driver/mysql + sqlc；跨库迁移工具 | 两个独立 storage adapter，共用领域代码与验收 | 目标库/Go 版本、快照/锁/提交未知、独立迁移、复合键、PG RLS、许可证；见 [第 12 章](12-portable-storage.md) |

这些是**评估候选，不是已选依赖**。协议库能减少实现面，但不会自动满足 Authova 的 App 隔离、登录 UI、密钥治理和管理权限。每个第三方依赖记录版本、许可证、传递依赖、漏洞更新频率和退出成本；正式开源协议/商标仍需产品决定。二开的稳定入口应是版本化 OpenAPI/事件/适配器、UI 主题与模板、部署配置；核心包仅在明确兼容政策后开放扩展。对二开方提供“自定义能力和升级路径”说明，不能暗示数据库表或任意内部接口长期稳定。

## 6.4 需要评审拍板的决定（按阻塞程度排序）

| 编号 | 具体问题 | 推荐起点 / 决策依据 | 最迟定稿阶段 |
| --- | --- | --- | --- |
| D1 | 5000+ QPS 是在线内省、refresh、登录的哪种组合？峰值维持多久、最大 App 占比多少？ | 当前按混合场景起草；给出真实业务峰值后冻结性能矩阵 | 阶段 0 |
| D2 | 是否允许各 App 自定义域名？issuer URL 是否固定 `.../a/{app_key}`？ | 首版固定单域路径；自定义域名涉及迁移、证书和发现兼容 | 阶段 0 |
| D3 | 首版哪些登录方式是必选，邮箱/短信供应商缺席时如何部署？ | 密码+邮箱验证为默认路径；短信与外部 OIDC 通过配置启用 | 阶段 0 |
| D4 | 访问令牌 TTL、内省使用范围、会话/封号撤销最长时限？ | 普通资源短期 JWT，高风险在线校验；先定威胁等级 | 阶段 0–1 |
| D6 | App 暂停与删除对旧离线令牌、用户导出/恢复意味着什么？ | 停发新 token 和拒绝在线请求；离线令牌仍需 TTL 窗口说明 | 阶段 1 |
| D7 | 生产最小部署依赖、所选数据库/Valkey 版本、KMS 方式和平台 operator 恢复流程？ | 关系事务库必备；正式目标含 PG/MySQL 两适配器。Valkey 在高吞吐/高可用画像建议，是否强制由故障基准决定 | 阶段 1 |
| D8 | 标识规范化、隐私保留、审计保留和地域数据要求？ | 先写可迁移的规则版本，按目标客户合规要求定保留 | 阶段 1 |
| D9 | Authova 自身使用什么开源协议、商标和贡献/安全响应规则？ | 公开前做依赖 SBOM 与法律审查，不从“Go 项目”推断可商用 | 阶段 4 前 |

产品差异化的可验证方向是：**在同一部署中严格独立的 App 身份域**、标准协议和可二开接口、可证明的跨 App 隔离、真实千万用户/热点 App 基准，以及可升级/恢复的自部署交付。它们目前都是设计目标，只有对应测试和运行证据通过后才能作为产品能力宣传。
